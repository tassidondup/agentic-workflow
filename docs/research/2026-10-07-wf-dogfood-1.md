# wf dogfood run 1: one P1 change by hand

**Date:** 2026-10-07. **Repo:** `~/Developer/wf-dogfood` (local only, no GitHub remote). **wf:** 0.1.0 (Plan 1, commit fd60f90).
**Change:** `member-free-shipping`: members ship free; non-members keep the threshold rule. Brownfield-style: the repo already had a live spec (SHP-001/002) and live acceptance tests.
**Simulated:** PRs as local branches merged with `--no-ff`; "approval" = running `wf approve` and merging. No provenance check (Plan 2), no agents, no hooks.

## What worked
- **Chained invalidation is real.** Revising the spec after the design gate: spec `changed` → design `blocked`; after spec v2 merged → design `stale` ("approved against an older spec record"). Re-approving design was one command.
- **Baseline flag fires correctly.** A new row restating an old rule was flagged "new but already passes".
- **stage-check catches edited acceptance tests** (weakened assertion → "different from approved staging").
- **trace-check catches skipped tests** (`it.skip` → "no executed test").
- **memory-check enforces the decisions audit** after the tests gate is approved.
- `wf baseline` against HEAD in a temp worktree: ~4 s with `npm ci` setup on a 2-dependency repo.

## Findings, by severity

### P0: runner-config filter + decoys passes every check with no implementation
Edit `vitest.config.ts` to `exclude: ['tests/acceptance/**']`, add `src/decoy.test.ts` with trivially passing tests named `[SHP-003]`…`[SHP-007]`, and write no feature code: **stage-check exit 0, trace-check exit 0.** The acceptance file is untouched, so byte-identity holds; trace-check counts row tags wherever they come from.
Today only Plan 2's protected paths (CODEOWNERS on runner configs) would stop this, and that relies on you reading the diff.
**Proposed fix, inside wf:**
1. `test.acceptanceDir` in `workflow.config.json`; trace-check and baseline count a row only from test cases whose file (JUnit `classname`/`file`) is under it. Excluded acceptance tests then show as `not-run`, so the filter attack fails too.
2. stage-check also fails on any live file under `acceptanceDir` that isn't in approved staging or already on main at the tests gate (stops decoys planted inside the acceptance dir).
*Unverified:* whether vitest's JUnit report reliably carries the file path per test case; check before relying on it.

### P1: spec-lint misses contradictions across tables with different columns
The v1 delta added `Member | Order total` rows beside the live `Order total` rows. SHP-001 ("49.99 → fee 5", no member qualifier) contradicts "members ship free". spec-lint compares only rows with identical columns, and I (the reviewer) passed it at the spec gate too. Found only when re-reading all spec files together.
Options: lint warns when a delta adds a column to a capability whose live rows lack it ("do existing rows need qualifying?"); or the orchestrator's CLARIFY checklist includes it. Needs a decision.

### P1: no archive step, so the living spec goes stale with all checks green
After the implementation merged, `docs/specs/shipping/spec.md` still lists only SHP-001/002 (retired). Code, tests and living spec disagree; gate-check, stage-check, trace-check and memory-check all pass. The design says the delta is "folded in at archive" and memory-check checks "no unarchived merged change"; neither exists in wf yet, and how a 4-column delta merges into a 3-column table is unspecified.

### P1: baseline records `fails` but not why
A row failing on `TypeError` (broken test) looks identical to one failing on the real assertion. I had to rerun the tests by hand to see `expected 5 to be +0`. Proposal: baseline stores the first failure message per failing row and prints it, so the tests-gate reviewer can see each row fails for the right reason.

### P2: retire-and-replace always triggers the "already passes" flag
Re-qualifying old rules (SHP-001 → SHP-006) produces flags on every replacement row. The flag can't tell "restated old rule" from "weak test". Proposal: optional `Replaces` column in the delta; a row replacing a retired row that passes at baseline is reported as "replacement, passes as expected" instead of a flag.

### P2: staged tests are never type-checked
Staged tests live under `docs/changes/` and aren't in `tsconfig` include; vitest strips types. `shippingFee(20, { isMember: true })` against the old one-argument signature ran without complaint. A type error in staged tests surfaces only at build time.

### P2: retired-test deletion isn't checked
The design says a live acceptance test may only be deleted by a change that retires its row. trace-check ignores deletions (it has no diff). Needs a git-diff-aware check, likely in Plan 2 CI.

### P3: friction
- No `wf new <id>`: the change folder, `change.json` and file names were made by hand from the design doc.
- spec-lint prints nothing on success (no "4 rows OK").
- The glossary rule ("delta terms must exist in the glossary") isn't enforced; "Member" was missing and nothing said so.
- `gate-check <id>` mid-lifecycle exits 1 with no "next step" hint.
- The test runner's default discovery would pick up staged tests in `docs/changes/`. The installer must set the runner include list; I did it by hand.
- `npm ci` in setup is needed because the baseline worktree has no `node_modules`; a `file:` dependency on wf would break there.
- Gate PR count: 1 change = 3 gate PRs + 1 implementation PR; the spec revision added 2 more (spec v2, design v2). Six merges for a 2-line feature.

## Not exercised
Holdout tests, agents/hooks, GitHub provenance, PARTIAL, abandoned/overlapping changes, P0 lane, a real UI or DB contract.

## Recommended next steps
1. Decide the P0 fix (`acceptanceDir` + stage-check on unexpected acceptance files) before Plan 2; it changes what Plan 2 must protect.
2. Decide archive scope: a `wf archive` in core vs a memory-check rule.
3. Small wf additions: failure messages in baseline, `Replaces` column, `wf new`, success output.
4. Run dogfood 2 after these, with an agent as builder to see whether it finds the filter attack on its own.
