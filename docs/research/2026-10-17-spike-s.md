# Spike S: agent teams, per-builder worktrees, hooks and Codex

**Date:** 2026-10-17. **Where:** `~/Developer/wf-dogfood`, branch `spike/s` (local only). **Versions:** Claude Code 2.1.301, lead on Opus 5.5, teammates on Sonnet, Codex CLI 0.155.1, in-process teammate mode, `auto` permission mode.
**Setup:** one lead and three teammates from role definitions (`builder-a`, `builder-b`, `reviewer`). A logging hook on PreToolUse, TaskCreated, TaskCompleted and TeammateIdle wrote every event, with its agent identity, to a JSONL log. The raw lead report and hook log stay in the scratch repo.
**Question:** can teammates each work in their own worktree, under hooks that enforce the workflow, with Codex callable from a teammate? This is the design's *Workspaces* caveat and its first two open questions.

## Results

## Findings
1. **Per-builder worktrees don't work with `EnterWorktree` and in-process teammates.** `EnterWorktree` scopes the *session*, and in-process teammates share one session. One builder entering a worktree takes everyone with it, the lead included. The design's caveat ("a spawned agent is either a teammate or worktree-isolated, not both", from the docs) is confirmed, and it's worse than written: a teammate can't safely enter a worktree after spawning either. *Verified 2026-10-17.*
2. **`TaskCompleted` also fires when a teammate goes idle holding an open task, and a blocking hook then loops.** builder-a never marked its task done, but the hook fired 24 times (final count), alternating with TeammateIdle about every 3 s. Every cycle wakes the teammate (cost), and messages sent to it during the loop ("hold", "stop", shutdown) were apparently never acted on. Any gate that blocks completion needs a loop guard: refuse at most N times per task, then escalate to the lead. *Verified; the cause is inferred from the event sequence.*
3. **Hooks can't find a builder's worktree from `cwd`.** `cwd` is the session's directory, so it's shared and can move. Map `teammate_name` (or `agent_type`) to a worktree through a registry the orchestrator writes. The payload's `teammate_name`, `team_name`, `task_id` and `task_subject` make this possible.
4. **The task tools are off by default on current models.** `TaskCreate`/`TaskList`/`TaskUpdate` are left out on models newer than Opus 4.7 / Sonnet 4.6 / Haiku 4.5 unless `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` is set before launch. Without them, TaskCreated and TaskCompleted never fire, and the design's build gate and done gate silently disappear. The first attempt at this spike failed exactly this way. Source: code.claude.com tools-reference, *Task tool availability*. *Verified 2026-10-17.*
5. **The harness has its own worktree write guard, stronger than our hook.** After `EnterWorktree`, it refuses Writes outside the worktree, and it refuses compound git commands it can't prove stay inside ("too complex to verify that it stays inside the worktree"). That's a real boundary, but it is session-wide (finding 1).
6. **Teammate context cost.** Writing a file triggers injection of the user's global rule files into teammates (all languages here). Trim the user-level rules or scope them per project before running teams.
7. **The worktree scope outlives the worktree.** When the worktree was removed during cleanup while the session was still open, the lead stayed confined to it. Reads of the main checkout worked, but Write, Edit and git there were refused until the session was resumed (`claude resume`). So never remove a worktree under a live session that entered it; end or resume the session first. *Verified 2026-10-17 (lead report, corrected copy on `spike/s`).*
8. **Ordering.** Spawning the reviewer before its input existed made it idle-wait and spend a nudge. The orchestrator should spawn a role when its task unblocks, not up front.

## Options for builder isolation (decision needed)
| Option | How | Status |
|---|---|---|
| **A. Hand-made worktrees, no `EnterWorktree`** | The orchestrator creates `.claude/worktrees/<role>` and writes a registry; builders `cd` explicitly in every command; hooks read the registry | Partly proven (builder-a's setup worked until finding 1 hit). No harness write guard; Bash unguarded. |
| **B. Split-pane teammates** (tmux) | Each teammate is its own process, so `EnterWorktree` might scope only that process | **Unverified**: needs a 30-minute follow-up probe. |
| **C. One builder at a time** | Builders run one after another in a single worktree per change; parallelism comes later | Works with everything verified here. Gives up parallel builds, which the design treats as optional anyway (open question: "cap parallel builders at 2"). |
| **D. Subagents with `isolation: worktree`** | Builders as subagents, not teammates; coordinate through files and the orchestrator | Documented. Loses the shared task list and peer messaging. |

**Decision (2026-10-17): C.** Recorded in the design doc v2.6, *Workspaces*.

**Recommendation (as proposed):** use **C** for the SiteOps pilot. It's the only option where everything needed is verified, and pilot changes are small. Run a short **Spike S2** on **B**, plus the untested P3b, P3c and P7, before Plan 4 commits to parallel builders. Whatever the choice: add the loop guard (finding 2), the worktree registry (finding 3) and `CLAUDE_CODE_ENABLE_TODO_TOOLS=1` (finding 4) to the installer and hooks.
