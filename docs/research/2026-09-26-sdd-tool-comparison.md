# SDD Tool Comparison — Phase 0 (desk research)

Date: 2026-09-26. Source: shallow clones of each repo (HEAD as of 2026-09-25) + READMEs/docs. **No tool has been run yet** — trial slice pending.

## Criteria scoring (0 = absent, 1 = possible with customization, 2 = native)

| Criterion | Spec Kit | OpenSpec | BMAD | superpowers |
|---|---|---|---|---|

## Findings
1. **No tool covers the core differentiator** (criterion 2): scenario tests authored by a different model from the example tables, locked against the implementer, plus row-level traceability and deterministic gates. That layer has to be built regardless of backbone — as Claude Code hooks + scripts + CI, independent of the workflow tool.
2. The workflow tools are mostly **prompt/artifact scaffolding**. They're swappable; the gates are not. Design the gates so the backbone can be replaced.
3. **BMAD: drop.** Heaviest ceremony, multi-role simulation is overhead for a solo user, tests come after code (the opposite of what we want), and it adds a Python runtime.
4. **Spec Kit vs OpenSpec is the real contest:**
   - Spec Kit wins on native `contracts/` + `data-model.md` and pre/post phase hooks.
   - OpenSpec wins on low overhead, a TS/Node runtime, living specs (brownfield-friendly as the pilot grows), and custom schemas that can model our exact artifact chain: `proposal → examples (tables) → contracts (OpenAPI) → migration → acceptance-tests → tasks`.
5. **superpowers** stays useful for the build step (plan → subagent TDD) but isn't a spec system.

## Tentative recommendation (to be confirmed by trial slice)
**OpenSpec with a custom schema** as the spec backbone + **our own gate layer** (hooks, traceability script, CI) + Codex for the acceptance-test and review steps. Spec Kit is the fallback if its contract/data-model handling proves materially better in the trial.

## Unverified / caveats
- The Uvik "SDD benchmark" (OpenSpec 42/50 merged vs 36/50 control) is a third-party vendor benchmark; methodology not reviewed.
- Spec Kit's preset mechanism for replacing the spec template wasn't tested.
- OpenSpec custom-schema limits (e.g. can an artifact be generated by a *different* agent?) are unknown. Likely not, which means the Codex step runs outside OpenSpec as a script.
