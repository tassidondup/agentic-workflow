How the workflow is built · design v2.2

Specs in. Proven, reviewed code out.

You write the specs and scenarios. An orchestrator runs a team of Claude roles, and Codex writes the tests and reviews the work. Every approval is bound to your account and to the exact bytes you approved, so no agent can fake one, including the orchestrator.

You Claude role Codex role Enforcement Repo file

What you do per change (P1)

  1. Write proposal.md and spec-delta.md: rule tables, journeys, UI states.
  2. Approve the spec gate PR, after answering the orchestrator's batched questions.
  3. Approve the design gate PR: contract diff, migration draft, mockups.
  4. Approve the tests gate PR: Codex's tests plus the baseline run.
  5. Merge the implementation PR once CI and the Codex review are green.

Everything else is agents. A P0 change (typo, dependency patch) skips the team and the gates, but must still pass every check.

    03 · Gates and approval records

    Approvals are chained. Break one and see what happens downstream.

    Each gate records the sha256 of the files it covers and the record it was approved against. It only counts if it reached main through a PR approved and merged by your account. Try the buttons: edit a file after approval, re-approve, or have the bot try to approve its own work.

    Implementation PR:allowed

    Red means the gate's own files changed after approval, or a gate upstream of it is invalid. Amber means its files are unchanged, but it was approved against an older upstream record and needs your re-approval.

    
      
    
    
    
  
    

  
  
    
    
    
      
    04 · Tests: staged, baselined, landed together
    
      
    Tests are locked by hash, not by sitting on main
    
      
    Example change: "limit listing prices to 1–1,000,000 and reject duplicate submits". Codex stages the tests, CI runs them against today's main to record a baseline, you approve both, and the implementation PR brings the code and the tests to main in one merge. Rows that already pass are fine; at least one must fail.

    05 · Messages coordinate, files decide
    
      
    What happens when two agents agree on something
    
      
    Agents can message each other directly. An agreement only counts once it's in a file, and if that file is covered by an approved gate, the gate breaks and the decision comes back to you through the orchestrator.
    
    
    
    
    
      
    
        
    
          
        
    
        
      
      
      
      
      
        
      
      
    
      
  
      

  
  
      
    
      
      
      06 · Planning dial
      
      
      How much process a change gets
      
      
      The orchestrator proposes a level and you confirm it. The question isn't "is this important?" but whether a wrong plan would be expensive, hard to undo, and invisible from inside.
      
    
      
    
      
      
      
      
      
      
      Would a wrong plan be expensive, hard to undo, and invisible to the agent that wrote it? If yes, go up a level.
